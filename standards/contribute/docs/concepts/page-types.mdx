Every page has one page type, based on [Diátaxis](https://diataxis.fr/). The type sets the page's structure and its template, and the skeleton folder sets the default type. Create a page from its template with `npx @wso2/docs new <type>`.

| Page type | Purpose | Default folder |
|---|---|---|
| [Quick start](#quick-start) | A working result in about 15 minutes, with few choices. | `get-started/` |
| [Tutorial](#tutorial) | Learn by building something end to end. | `get-started/` |
| [How-to](#how-to) | One task: goal, prerequisites, steps, verify, troubleshoot, next. | `guides/`, `deploy-and-operate/` |
| [Concept](#concept) | What something is and why, with no steps. | `concepts/` |
| [Reference](#reference) | Facts to look up: configuration, APIs, CLI, error codes. | `reference/` |
| [Release notes](#release-notes) | What changed in a version or a Cloud release. | `release-notes/` |

The migration's special layouts count as variants and keep their layout: `complete-guide` (how-to), `sdk` (reference), `connector` (reference), `api-reference` (reference).

## Quick start {#quick-start}

A working result in about 15 minutes, with few choices. Front matter: `type: quick-start`. Default folder: `get-started/`.

**Structure**

- One or two sentences on what the reader will have working at the end.
- `## Before you start`: accounts, tools and versions, as a short list.
- One `##` section per stage, each a numbered list with one action per step.
- `## See it work`: what the reader runs or opens to confirm the result.
- `## Next steps`: two or three links onward.

**What reviewers check**

- Finishes in about 15 minutes, with defaults chosen for the reader.
- Every step is testable and produces a visible result.
- No branching paths or optional detours; link to how-to pages instead.

## Tutorial {#tutorial}

Learn by building something end to end. Front matter: `type: tutorial`. Default folder: `get-started/`.

**Structure**

- What the reader will build and what they will learn.
- `## Prerequisites`.
- One `##` section per stage of the build, each ending with a result the reader can check.
- `## What you learned` and `## Next steps`.

**What reviewers check**

- Each stage ends with something the reader can see or run.
- Explains why at each stage, briefly; concepts link to concept pages.

<details>
<summary>The tutorial template</summary>

````mdx

## How-to {#how-to}

One task: goal, prerequisites, steps, verify, troubleshoot, next. Front matter: `type: how-to`. Default folder: `guides/`, `deploy-and-operate/`.

**Structure**

- One or two sentences stating the task and its outcome.
- `## Prerequisites`: required role, installed components, credentials.
- One or more `##` sections named with an imperative verb phrase, each a numbered list of steps.
- `## Verify`: how the reader knows it worked.
- `## Troubleshooting` (optional): known failures and their fixes.
- `## Next steps`.

**What reviewers check**

- Covers exactly one task; a second task is a second page.
- Steps are numbered, one action each, and copy-pasteable where they are commands.
- Has a verify section with an observable result.

<details>
<summary>The how-to template</summary>

````mdx
---

description: __DESCRIPTION__
type: how-to
---

{/* How-to: one task. Goal, prerequisites, steps, verify, troubleshoot, next. A second task is a second page. */}

## Do the task

{/* Name this section with an imperative verb phrase, such as "Register the application". */}

## Concept {#concept}

What something is and why, with no steps. Front matter: `type: concept`. Default folder: `concepts/`.

**Structure**

- Opens by defining the thing and its scope.
- `##` sections on how it works, when to use it and its limits.
- `## Related` links to how-to and reference pages.

**What reviewers check**

- No imperative instructions; link to the how-to instead.
- Says what is specific to this product, not generic background.

<details>
<summary>The concept template</summary>

````mdx
---
title: __TITLE__

## Reference {#reference}

Facts to look up: configuration, APIs, CLI, error codes. Front matter: `type: reference`. Default folder: `reference/`.

**Structure**

- One sentence on what the reference covers.
- Tables or definition lists, grouped under `##` headings.
- Defaults, types, allowed values and examples for every entry.

**What reviewers check**

- Tables over prose; no narrative and no "you should".
- Every entry has its type and default.

<details>
<summary>The reference template</summary>

````mdx
---
title: __TITLE__
description: __DESCRIPTION__

## Release notes {#release-notes}

What changed in a version or a Cloud release. Front matter: `type: release-notes`. Default folder: `release-notes/`.

**Structure**

- The version or release date, and one sentence summarizing the release.
- `## New features`, `## Improvements`, `## Fixed issues`, `## Deprecated and removed features`, `## Known issues`; leave out empty sections.

**What reviewers check**

- Each item says what changed for the reader and links to the page that covers it.
- Deprecations name the replacement and the removal version.

<details>
<summary>The release notes template</summary>

````mdx
---
