A Content repository holds the content of one or more Doc spaces, each in its own directory. It holds no site tooling: the Platform builds every Docs deployment from it. A Docs release is a tag in the Content repository, and it is the source of one Edition.

## How it works

### The layout

`docs-api-platform` holds three Doc spaces:

```text
docs-api-platform/
├── README.md  CODEOWNERS            shared files only at the root
├── .github/workflows/docs.yml       one workflow, path-filtered: it acts on the Doc spaces a change touches
├── .github/workflows/docs-sync.yml  optional: bot pull requests for generated content
├── .github/branch-ruleset.json      the branch protection to import
├── .vscode/                         editor settings, from the Platform's template
├── api-platform/                    API Platform Cloud: family-level, Cloud only
├── api-manager/                     API Manager: 4.7.0, 4.6.0
└── ai-gateway/                      AI Gateway: Cloud part of api-platform, plus 1.2.0 and 2026.09.24
    ├── docspace.yaml                the Doc space manifest
    ├── editions.yaml                {edition.*} variables for Cloud and Self-hosted
    ├── redirects.yaml               page moves and legacy URLs
    ├── docs/                        the pages; folders are the menu tree
    │   ├── index.mdx
    │   └── get-started/  guides/  concepts/  reference/  deploy-and-operate/  release-notes/
    ├── partials/                    snippets shared inside this Doc space only
    └── assets/                      images and files; cloud/ and self-hosted/ for Edition-only ones
```

Every Doc space has its own directory, named by its slug, even in a repository with one Doc space. The directory's `docs/` starts with the common skeleton folders. API specs sit next to their reference page. Partials are never shared across Doc spaces.

The workflows, the branch ruleset and the editor settings come from `templates/content-repo/` in the Platform, and `npx @wso2/docs init` writes them with a new Doc space's directory. The repository never holds React code, plugins or CSS. See [Extension points](extension-points.mdx).

### What each branch builds

- **`main`** holds every Doc space's main line.
  - A Doc space with a Cloud Edition builds Cloud from it.
  - A Cloud part's main line is its part of the platform's Cloud tree.
  - A Doc space with Self-hosted versions only, such as API Manager, previews `main` as `next`, the coming version. `next` is never published.
- **`<doc space>/release/<version>`**, such as `ai-gateway/release/1.2.0`, is one Self-hosted version. It is a copy of the whole repository, made by a Branch cut from `main` with `npx @wso2/docs branch-cut`, which also removes the markers the version covers from `main` and writes the branch cut report. Its build reads only its own Doc space's directory. A check blocks pull requests that change any other path there.

A repository with one Doc space may keep unprefixed `release/<version>` branches. A repository with several needs the prefix.

### Docs releases

A Docs release is a tag. A version's docs may be released many times, independently of the product's own release.

| Edition | Tag | Made by |
|---|---|---|
| A Self-hosted version | `<doc space>/<version>-docs.<n>`, such as `ai-gateway/1.2.0-docs.3` | The **Release docs** run of the repository's Docs workflow, on the version's branch |
| Cloud | `<doc space>/cloud-<YYYY.MM.DD>.<n>`, such as `api-platform/cloud-2026.10.26.1` | Every merge to `main` that touches the Doc space or one of its Cloud parts |

An Edition's source is its Content repository, its Doc space directory and its branch's newest Docs release tag. So a re-release needs no manifest change. The Doc space manifest can `pin` one Edition to a tag to hold it there: releases of its other tags are refused until the pin is removed.

A change to a Cloud part releases its platform: a merge that touches `ai-gateway/` on `main` makes the next `api-platform/cloud-…` tag. A part has no Cloud tag of its own.

### What a Docs release publishes

Every Docs release tag gets a Docs bundle. In the same run that makes the tag, the repository's `docs.yml` calls the Platform's `docs-bundle.yml` at `v1`. It checks the tagged commit, packs the Doc space directory as it is in the repository, Edition markers included since the build applies them, with a `bundle.json` that records the repository, tag, Edition and source commit, and publishes the zip as a GitHub Release named after the tag. A Self-hosted bundle leaves out `assets/cloud/`. A family Cloud's bundle holds the family directory and each Cloud part's directory.

The Platform then releases the bundle:

1. Within half an hour, the Platform finds the release, verifies its bundle (its digest, that the Platform's `docs-bundle.yml` made it, that it unpacks safely and carries no code) and records it. If it can't accept it, it opens an issue that mentions the Doc space's owners.
2. The Platform composes the Deployment manifest from every Content repository's `main`, and keeps it as the release's copy.
3. It builds each Docs deployment the tag makes from the bundle, and runs the blocking checks again. A failed check publishes nothing, and the previous release stays live.
4. It uploads each build to its own release folder, then switches the deployment to it in one step.
5. The staging crawl must pass before the same files go to production.

To withdraw a Docs release, delete its GitHub Release: the Platform moves its Edition back to the release before it.

A family Cloud is one Docs deployment. Its build reads each Cloud part's directory from the same bundle, so the whole tree is one commit.

The first Self-hosted Edition in the Doc space manifest's order is also built as `latest`. That Edition's tag makes two Docs deployments: `/<doc space>/<version>/` and `/<doc space>/latest/`. Cloud is never built twice.

Releases need no work from the Platform team. A Platform release rebuilds every live Docs deployment of the repositories that pin its major (`v1` in `docs.yml`), with no new Docs release.

## Limits

- The Platform's workflows need secrets while the repositories are private: `DOCS_PLATFORM_READ_TOKEN` in each Content repository, to check out the Platform, and `CONTENT_READ_TOKEN` in the Platform, to read the Content repositories. These are set up with WSO2 infra. Releases and the Branch cut need no other secret: they use the workflow token.
- Turn on immutable releases in each Content repository, so a published Docs bundle can't change. `wso2-docs init` reminds you.
- A Docs bundle holds at most 1 GiB and 30,000 files, with a warning above 500 MB. Pages carry no code of their own: see [Content safety](../../reference/checks.mdx#content-safety).
- Docs release tags come only from the workflow. A tag ruleset keeps others from making them. See [Protect the main and release branches](../../guides/owners/branch-protection.mdx).
- In a repository with one Doc space, tags may leave out the `<doc space>/` prefix.
